# Docker Stack Management — Design Spec

## Overview

Add GitOps-style Docker stack management to homelab-manager. Users define stacks as docker-compose files in a git repository managed by homelab-manager. Changes — via an in-app editor or `git push` — trigger deployments to Docker hosts through lightweight agent containers.

**Feature flag:** `DOCKER_MANAGEMENT_FEATURE_FLAG=true` (env var). Undocumented for v1. When off, the existing monitoring-only Docker page is unaffected.

## Architecture

```
User's IDE ──git push──▶ homelab-manager git server ──post-receive──┐
                                                                     ▼
User's Browser ──UI edit──▶ homelab-manager commits ──────────────▶ Deploy Pipeline
                                                                     │
                                         ┌───────────────────────────┤
                                         ▼                           ▼
                                    Agent (host-1)              Agent (host-2)
                                    via socket proxy            via socket proxy
```

### Components

1. **Agent container** — lightweight Bun HTTP server on each Docker host
2. **isomorphic-git** — git repo management inside homelab-manager (no external git server)
3. **Deploy pipeline** — trigger-agnostic orchestration layer
4. **UI** — stacks page, compose editor, deploy controls
5. **OpenBao** — secrets management (dev server, feature-flagged)

## 1. Agent Container

A lightweight Bun HTTP server deployed as a Docker container on each managed host. Replaces the current direct Dockerode connection for both monitoring and deployment.

### Responsibilities

- Execute `docker compose` commands for stack deployment
- Stream container stats (replaces current Dockerode stats streaming)
- Stream container logs
- Accept deploy/teardown requests
- Report heartbeat to homelab-manager

### Docker Socket Proxy

The agent connects to Docker via a socket proxy (e.g., Tecnativa/docker-socket-proxy) rather than mounting `/var/run/docker.sock` directly.

**Required socket proxy permissions:**

| Permission | Reason |
|------------|--------|
| `CONTAINERS=1` | List, inspect, create, start/stop, remove containers |
| `IMAGES=1` | Pull images for compose deployments |
| `NETWORKS=1` | Create/manage networks for compose stacks |
| `VOLUMES=1` | Create/manage volumes for compose stacks |
| `POST=1` | Required for write operations |

**Not required:** `EXEC`, `SERVICES`, `SWARM`, `NODES`, `BUILD`, `SECRETS`, `CONFIGS`. No privileged mode or host network mode needed.

### API Surface

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/health` | GET | Heartbeat + host info (Docker version, resources) |
| `/stats/stream` | GET | SSE stream of all container stats |
| `/logs/:containerId` | GET | SSE stream of container logs |
| `/stacks/deploy` | POST | Receive compose file + env, run `docker compose up -d --remove-orphans` |
| `/stacks/teardown` | POST | Run `docker compose down` for a stack |
| `/stacks/restart` | POST | Run `docker compose restart` for a stack |
| `/stacks/status` | GET | List running stacks and their container states |

### Authentication

Shared token generated by homelab-manager during agent bootstrap. Passed via `Authorization: Bearer <token>` header on every request. Token is stored as a bcrypt hash in the `managed_hosts` table (never plaintext). The agent receives the plaintext token as an env var at creation time and compares incoming requests against it.

### Agent Environment

```yaml
environment:
  DOCKER_HOST: "tcp://socket-proxy:2375"
  AGENT_TOKEN: "<generated-by-homelab-manager>"
  AGENT_PORT: "9090"
volumes:
  - homelab-stacks:/opt/homelab-manager/stacks
```

### Working Directories

Each stack gets a persistent directory on the host, stored in a named Docker volume (`homelab-stacks`) mounted at `/opt/homelab-manager/stacks/`:

```
/opt/homelab-manager/stacks/
├── plex/
│   ├── docker-compose.yml
│   └── .env
├── traefik/
│   ├── docker-compose.yml
│   └── .env
```

On deploy, the agent overwrites the compose file and `.env`, then runs `docker compose up -d`. Docker Compose handles the diff — only recreates containers that changed. The volume persists across agent restarts and redeployments.

### Docker Compose CLI Dependency

The agent container image must include the `docker compose` CLI binary (v2). The agent executes compose commands via `Bun.spawn()` subprocess calls. The `DOCKER_HOST` env var ensures compose commands route through the socket proxy.

### Image & Development

- **Production:** Published to GHCR alongside homelab-manager
- **Dev mode:** Built from source locally via `docker-compose.dev.yml`
- Agent source lives in `agent/` directory at project root
- Dev mode supports hot reload via volume mount + `--watch`

## 2. Git Management (isomorphic-git)

### Repository Storage

Bare git repos stored in a Docker volume (`homelab-manager-repos`). One repo per setup — all stacks in a single repo.

### Repo Structure

```
repo/
├── manifest.yaml
├── plex/
│   └── docker-compose.yml
├── traefik/
│   └── docker-compose.yml
└── pihole/
    └── docker-compose.yml
```

### Manifest Format

```yaml
stacks:
  plex:
    host: homeserver
    auto_deploy: true
  traefik:
    host: homeserver
    auto_deploy: false
  pihole:
    host: pihole-host
    auto_deploy: true
```

Host assignment lives in the manifest, not the directory structure. Stacks are decoupled from hosts — moving a stack to a different host is a one-line manifest change.

**Terminology note:** "Stack" in this context refers to a Docker Compose project (a set of services defined in a single `docker-compose.yml`). This is distinct from Docker Swarm's `docker stack` command. The `COMPOSE_PROJECT_NAME` is set to the stack's directory name (e.g., `plex`, `traefik`). Manifest `host` values must match a `managed_hosts.name` record in the database.

### Git Server

Homelab-manager exposes an HTTP git endpoint for clone and push support. Note: isomorphic-git is a client-side library and does not provide a smart HTTP server implementation. The git server endpoint will shell out to `git upload-pack` and `git receive-pack` CLI commands (the standard approach used by most git HTTP servers, including Gitea/Forgejo). The `git` binary is required in the homelab-manager container image.

```bash
git clone http://homelab-manager:3000/api/git/repo
git push origin main
```

### Post-Receive Flow

1. Push arrives at the git server endpoint
2. Diff new commit against previous HEAD
3. Identify changed stacks (directories with modified files)
4. For each changed stack, check manifest `auto_deploy` setting
5. Auto-deploy stacks: build `DeployRequest`, send to pipeline
6. Manual-approval stacks: create pending deploy record in PostgreSQL, surface in UI

### In-App Editing

- UI reads files via isomorphic-git from the bare repo
- Edits create commits directly (author = authenticated user)
- Same post-receive logic triggers after commit

### Branch Model

`main` only for v1. Multi-branch/environment support is a future concern.

## 3. Deploy Pipeline

Trigger-agnostic orchestration. Receives a `DeployRequest` and executes it.

### DeployRequest Shape

```typescript
interface DeployRequest {
  stack: string
  host: string
  composePath: string
  commitSha: string
  secrets: Record<string, string>
  action: 'deploy' | 'teardown' | 'restart'
  autoApproved: boolean
}
```

Two builders produce this same shape:

- `GitTriggerBuilder` — from a git push event
- `UITriggerBuilder` — from a UI action

Additional triggers (webhook, API, scheduled) can be added later without touching the pipeline.

### Pipeline Stages

```
DeployRequest
  │
  ▼
1. Validate ──▶ Stack exists in manifest? Host name matches managed_hosts.name?
  │              Agent healthy? Compose file valid YAML with required top-level keys?
  │
  ▼
2. Resolve secrets ──▶ Read ${VAR} references from compose file
  │                     Fetch values from OpenBao (when enabled)
  │                     Build .env file content server-side
  ▼
3. Dispatch ──▶ POST to agent: compose file + .env content
  │              Timeout: 5 minutes. Retry: none (fail fast, user can retry manually)
  ▼
4. Agent executes ──▶ Overwrite compose + .env in working directory
  │                    Run `docker compose up -d --remove-orphans`
  │                    Stream output back to homelab-manager
  │                    Agent unreachable → status: `failed`, logs: connection error
  ▼
5. Record result ──▶ Store deploy record in PostgreSQL
```

### Change Detection

| Compose changed | Env changed | Result |
|----------------|-------------|--------|
| No | No | `no_change`, skip |
| Yes | No | Deploy |
| No | Yes | Deploy |
| Yes | Yes | Deploy |

Env change detection uses a hash of the resolved `.env` content compared against the last deploy's stored env hash (hash only, not values). First deploy of a stack (no previous deploy record) always triggers a deploy.

### Deploy States

- `pending` — awaiting manual approval
- `in_progress` — dispatched to agent
- `succeeded` — agent reported clean exit
- `failed` — agent reported error or timeout
- `no_change` — skipped, already up to date

### Deploy History Schema

```sql
deploy_history (
  id SERIAL PRIMARY KEY,
  stack TEXT NOT NULL,
  host TEXT NOT NULL,
  commit_sha TEXT NOT NULL,
  env_hash TEXT NOT NULL,
  status TEXT NOT NULL,
  trigger TEXT NOT NULL,  -- 'git_push' | 'ui' | 'manual_rollback'
  logs TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
)
```

### Concurrency

One deploy per stack at a time. Different stacks deploy independently. Deploy queue is maintained in PostgreSQL (deploy records with `pending` status, ordered by `created_at`). If multiple pushes arrive during a deploy, only the latest pending request executes — intermediate commits are skipped since the latest commit includes all changes. On homelab-manager restart, pending deploys are resumed from the database.

### Rollback (v1)

Manual only. User selects a previous commit from history, clicks deploy. Pipeline builds a `DeployRequest` with the old `commitSha` and deploys that version.

## 4. UI & Frontend

### Feature Flag Gate

All Docker management UI conditionally rendered when `DOCKER_MANAGEMENT_FEATURE_FLAG` is set. Existing monitoring page unaffected when off.

### New Route: `/docker/stacks`

Stacks management page with:

- **Stack list** — name, host, sync status (in-sync / pending / failed), deploy mode (auto/manual)
- **Expanded stack detail** — diff view for pending changes, variables panel, deploy/logs/edit/history actions
- **Editor view** — Monaco editor (dynamically imported to avoid bundle impact) for compose files with `monaco-yaml` plugin for Docker Compose schema validation and autocomplete. Side panel for `${VAR}` references with secret inputs
- **Deploy history** — per-stack list of deploys with commit, timestamp, trigger, status, collapsible logs

### Existing Docker Page Enrichment

- Containers get a "Stack" label badge when they belong to a managed stack
- Badge links to the stack on `/docker/stacks`

### Agent Status

Host cards show agent connection state (connected / disconnected / degraded).

### Component Reuse

| Existing Component | Reuse For |
|-------------------|-----------|
| `ContainerTable` pattern | Virtualized stack list with expand/collapse |
| `ContainerRow` layout | Stack row (same rhythm, same expand pattern) |
| `ContainerChartsCard` expand | Stack detail expansion |
| `ContainerLogViewer` | Deploy log output |
| `IconPickerDialog` | Stack icons |
| `MetricSparkline` | Deploy frequency or uptime sparklines |
| `HistoricalTimeline` | Deploy history timeline |

### Styling

- TailwindCSS only (no `sx` props, no new `.css` files)
- Theme CSS variables for all colors
- New CSS variables in `App.css` for deploy status:
  - `--chart-deploy-success`
  - `--chart-deploy-failed`
  - `--chart-deploy-pending`
- MUI components for interactive elements

## 5. Agent Bootstrap & Host Management

### Initial Setup (per host)

1. User adds a host in the UI — provides Docker socket proxy URL
2. Homelab-manager connects via Dockerode to the proxy
3. Pulls (prod) or builds (dev) the agent image
4. Deploys agent container through the proxy
5. Generates a unique token, passes as env var to agent
6. Stores host record in PostgreSQL (host name, agent URL, token)
7. Agent starts, confirms healthy via `GET /health`
8. All communication switches to the agent

### Host Configuration

Moves from env vars to database records:

```sql
managed_hosts (
  id SERIAL PRIMARY KEY,
  name TEXT UNIQUE NOT NULL,
  agent_url TEXT NOT NULL,
  agent_token_hash TEXT NOT NULL,  -- bcrypt hash, never plaintext
  socket_proxy_url TEXT NOT NULL,
  agent_version TEXT,
  status TEXT DEFAULT 'pending',
  created_at TIMESTAMPTZ DEFAULT NOW()
)
```

### Migration Path

Existing `DOCKER_HOST_N` env var hosts continue to work for monitoring-only (feature flag off). New agent-based hosts are added through the UI when the feature flag is on.

### Agent Updates

On homelab-manager update, agent versions are checked via `GET /health` (which returns the agent version). If outdated, the UI offers to update. The update is performed by homelab-manager connecting directly to the host's socket proxy URL (stored in `managed_hosts.socket_proxy_url`) via Dockerode — bypassing the agent itself. This avoids the circular dependency of an agent replacing its own container. The sequence: pull new image → stop old container → start new container with same config → verify health.

### Dev Mode

Agent built from source in `docker-compose.dev.yml`:

```
homelab-manager/
├── src/                    # web app
├── worker/                 # existing worker
├── agent/                  # agent source
│   ├── Dockerfile
│   ├── src/
│   │   └── index.ts
│   └── package.json
└── docker-compose.dev.yml
```

## 6. OpenBao Integration (Feature-Flagged)

OpenBao is an optional sub-feature within Docker management. It activates when `OPENBAO_URL` is set (e.g., `OPENBAO_URL=http://openbao:8200`). When not set, secrets UI is hidden and stacks use whatever `.env` files already exist on the host's working directory. The `docker-compose.dev.yml` includes the OpenBao dev server by default when `DOCKER_MANAGEMENT_FEATURE_FLAG` is on, but it can be removed without breaking stack management.

### Dev Setup

Added to `docker-compose.dev.yml`:

```yaml
openbao:
  image: openbao/openbao
  command: server -dev
  environment:
    BAO_DEV_ROOT_TOKEN_ID: "dev-root-token"
  ports:
    - "8200:8200"
```

Dev server only. No production config, no unseal ceremony, no persistence. Not included in the self-hosted example.

### Integration

- OpenBao client in `src/lib/clients/` — thin wrapper around OpenBao HTTP API
- Secrets stored at `secret/stacks/<stack-name>/<key>`
- Homelab-manager authenticates with dev root token

### Secret Lifecycle

1. User edits compose file, references `${MY_SECRET}`
2. Editor detects variable, shows input in side panel
3. User sets value → stored in OpenBao at `secret/stacks/<stack>/MY_SECRET`
4. On deploy, pipeline reads all secrets for the stack from OpenBao, builds `.env`
5. Reveal in UI → single authenticated API call to OpenBao, value displayed briefly

### Secret Security

- API returns secret **names and metadata only** on load, never values
- Reveal requires a separate authenticated request for a single secret
- Values never cached client-side
- Secrets flow server-side only during deploy: OpenBao → homelab-manager → agent
- Future: PocketID OIDC integration for access control, potential WebAuthn PRF for additional key derivation

### When OpenBao Is Not Configured

No secrets UI, no env injection. The deploy pipeline skips the "Resolve secrets" stage. Stacks use whatever `.env` files already exist in the agent's working directory on the host. Users manage those files manually.

## v1 Scope

### Included

- Agent container (Bun HTTP server, socket proxy, stats + logs + deploy)
- isomorphic-git repo management with HTTP smart protocol
- Manifest + compose file structure
- Deploy pipeline (trigger-agnostic, `DeployRequest` shape)
- Git push and UI edit triggers
- Auto-deploy and manual-approval per stack
- Stacks UI page with editor, diff view, deploy controls, history
- Agent bootstrap via Dockerode
- OpenBao dev server for secrets (feature-flagged)
- Dev mode: agent built from source
- Change detection (compose + env hash diffing)

### Deferred to v2+

- Rollback UX improvements
- Deploy history timeline visualization
- Stack health checks (post-deploy verification)
- Secret rotation
- Notifications on deploy success/failure
- Multi-branch environments
- PocketID OIDC integration
- Production OpenBao setup (auto-unseal, persistence)
- Stack templates / marketplace
- Dependency ordering across stacks
- Scheduled deploys
